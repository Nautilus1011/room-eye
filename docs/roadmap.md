# ロードマップ

room-eye 全体の開発計画と現在地。機能別の詳細計画は `plans/` を参照。

## 最終的なゴール

ラズパイ + カメラ + 物体検出による自室のスマートホーム化。

1. **カメラ自動追尾**（パン・チルト制御） ← 現在の主対象
2. ハンドジェスチャー認識 → PC の Wake on LAN・扇風機・照明の制御
3. 床の空き面積算出 → 部屋の散らかり度の定量化
4. 物体カウント（コップ・ペットボトル等）→ 片付け通知

## 実装言語の方針

**Python で検証し、C/C++ で運用する。**

Python フェーズの真の成果物は Python コードではなく、**検証済みのパラメータ値とアルゴリズム仕様**である。
この前提が、レイヤ構成（`design/architecture.md`）と設定管理方式（`adr/0001-no-hydra-on-rpi.md`）の
両方を決めている。

### Pre — ハードウェア単体動作確認 ✅

`experiment/pan_tilt_camera_check/`

サーボ 2 軸（GPIO14 / GPIO15）とカメラの動作、180 度回転補正の確認。完了。

判明した課題:

- `PWMSoftwareFallback` 警告。ソフトウェア PWM のジッタにより、PWM 保持中にサーボが微振動する
- 現状は「角度指定 → 待機 → `detach()` → 待機 → 撮影」で回避しているが、**この回避策は追尾では使えない**
  （追尾は連続的に保持しながら動き続ける必要がある）

詳細は `experiment/pan_tilt_camera_check/EXPERIMENT.md` を参照。

### Phase 0 — コードベースの整理 🚧

**目的**: サーボ制御・カメラ撮影処理を恒久的な置き場に移し、以降のフェーズで再利用できる形にする。
同時に、C/C++ 移植を見据えたレイヤ分割を最初に入れておく。

**済んでいること**（`experiment/pan_tilt_camera_check/scripts/`）:

- スクリプト間で重複していたサーボ生成・可動域クランプ・Picamera2 のライフサイクル管理を
  `servo.py`（`build_servo` / `clamp` / `PanTilt`）と `camera.py`（`PanTiltCamera`）に分離
- context manager による解放の保証（`try/finally` の手書きを解消）
- 各スクリプトは設定読み込みと CLI 引数処理のみを担う形になった

**残っていること**:

- **恒久的な置き場への移設**。現在は `experiment/` 配下（使い捨て可の領域）にあり、
  移植対象のリファレンス実装を置く場所として適切でない
- **レイヤ分離**。`clamp` が `gpiozero` を import する `servo.py` に同居しており、
  実機なしで import できない。`control/` に移す必要がある
- `dataclass` ベースの型付き設定 + 素の YAML ローダ（現在は `dict` を直接受け渡し）
- `hal/` の遅延 import（現在はモジュールトップで `gpiozero` / `picamera2` を import）
- ハードウェア定義（GPIO・可動域・パルス幅）の `config/hardware.yaml` への集約（現在 2 つの YAML に重複）
- ディレクトリ構成の確定（[ADR-0002](adr/0002-directory-layout.md)）に沿った `room_eye/` の作成

**完了条件**:

- `control/` が実機なしで import・単体テストできる
- 実機で既存 3 スクリプトが従来どおり動作する（**挙動を変えないリファクタなので回帰確認が主眼**）
- 構文チェックが通る

### Phase H — サーボ PWM 品質の改善

**目的**: 追尾に耐える PWM 信号品質を確保する。

Phase 2 では「連続保持しながら滑らかに動かす」必要があり、Pre フェーズの `detach()` 回避策が使えない。
そのため PWM のジッタ対策が追尾実装の前提条件になる。

**背景**: GPIO14 / GPIO15 はハードウェア PWM ピンではないため、ソフトウェア PWM で駆動されている。

**選択肢**（詳細と検証手順は `plans/auto-tracking.md`）:

1. ハードウェア PWM ピンへの配線変更
2. PCA9685（I2C サーボドライバ）の導入
3. ソフトウェア PWM のまま、制御側で許容する

> ⚠️ `EXPERIMENT.md` に記載した「`pigpiod` への切り替え」は、**Raspberry Pi 5 では使えない**可能性が高い。
> 最初に `cat /proc/device-tree/model` でモデルを確認すること。

**完了条件**: 連続保持中の微振動が追尾に支障ない水準であることを、定量的に確認できている。

### Phase 1 — 物体検出の実現可能性検証

**目的**: ラズパイ CPU 上で追尾に使える推論速度が出るかを実測し、モデルと入力解像度を決める。

ここで速度が出なければ追尾の設計自体が変わるため、Phase 2 より先に測る（`.claude/rules/cv-research.md`）。

**完了条件**: モデル・入力解像度・推論パラメータが実測値に基づいて確定し、目標 FPS の達成可否が判断できている。

### Phase 2 — 閉ループ追尾の実装

**目的**: 検出結果からサーボ角を決める制御ループを Python で実装し、実機でチューニングする。

**完了条件**: 静止目標を画面中心に保持でき、移動目標に追従できる。ハンチングが実用上問題ない水準。

### Phase 3 — 仕様の凍結とゴールデンデータの作成

**目的**: C/C++ 移植の受け入れ基準を作る。

Python 版で「bbox 座標の時系列」を入力、「出力されたサーボ角の時系列」を期待値として記録し、
**言語をまたいだ回帰テストのゴールデンデータ**とする。C++ 版に同じ入力を与えて出力の一致を検証できるため、
実機なしで移植の正しさを確認できる。`control/` を外部依存ゼロの純粋関数にしておく理由がこれ。

**完了条件**: 確定パラメータ・アルゴリズム仕様・ゴールデンデータが揃っている。

### Phase 4 — C/C++ への移植

**目的**: 運用版の実装。方針は `design/cpp-migration.md`。

移植順序は `control/`（純粋ロジック）→ `hal/`（ハードウェア）→ `perception/`（推論）。
`control/` から始めるのは、ゴールデンデータで実機なしに検証でき、移植の足場が固まるため。

> **未決**: 全面移植か、性能critical な層だけ C++ 化する hybrid かは確定していない。
> ロボティクスの現場では後者（C++ コア + Python バインディング）が主流。
> Phase 1 の実測値が出てから決め、決まった時点で ADR を追加する。詳細は `design/cpp-migration.md`。
