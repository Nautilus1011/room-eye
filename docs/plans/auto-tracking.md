# カメラ自動追尾 — 実験・開発方針

パン・チルト 2 軸のサーボと物体検出を組み合わせ、対象を画面中心に保持し続ける自動追尾を実現する。
全体のフェーズ区分は `../roadmap.md`、レイヤ構成は `../design/architecture.md` を参照。

## 目的

検出した対象の画像上の位置から、対象を画面中心に保つためのパン・チルト角を継続的に算出・指令する
閉ループ制御を、ラズパイ実機上で実用的な応答速度・安定性で成立させる。

最終的には C/C++ で運用するため、**Python フェーズのゴールは「動くコード」ではなく
「確定したパラメータ値と、移植可能なアルゴリズム仕様」**である。

## 前提と制約

### ハードウェア（`.claude/rules/hardware.md`）

| 項目 | 値 |
| :--- | :--- |
| パン軸 | GPIO14（BCM）。正面 0°、可動域 -90°〜+90° |
| チルト軸 | GPIO15（BCM）。水平 0°、直上 90°（マイナス方向には倒さない） |
| カメラ取付 | 配線の都合で物理的に 180 度回転。取得画像は必ず回転補正が必要 |

- 可動域を超える角度指定は行わない。**ソフト側で必ずクランプする**
- UART を有効化していると GPIO14/15 と競合するため、シリアルコンソールは無効化しておく

### 前フェーズで判明している課題

`experiment/pan_tilt_camera_check/EXPERIMENT.md` より:

- `PWMSoftwareFallback` 警告が出ており、**PWM 保持中にサーボが微振動する**
- 現状の回避策は「角度指定 → `settle_wait_sec` 待機 → `detach()` → `hold_release_wait_sec` 待機 → 撮影」
- ⚠️ **この回避策は追尾では使えない。** 追尾は連続的に保持しながら動き続ける必要があり、
  撮影のたびに PWM を切ることができない

したがって PWM 品質の改善（Phase H）が追尾実装の前提条件になる。

## 制御アルゴリズムの設計方針

すべて `src/room_eye/control/` に外部依存ゼロの純粋関数として実装する
（Phase 3 のゴールデンデータによる言語横断テストの前提。`../design/cpp-migration.md`）。

### 1. 画像座標 → 角度偏差の変換

180 度回転補正済みの画像を前提とし、画像左上原点・y 軸下向きとする。

```
Δθ_pan  = (cx - W/2) / W × HFOV
Δθ_tilt = (cy - H/2) / H × VFOV
```

`cx, cy` は bbox の中心、`W, H` は画像サイズ、`HFOV/VFOV` はカメラの画角。
`HFOV / W` が「1 ピクセルあたり何度か」に相当し、これが制御の基準ゲインになる。

理論上はこの偏差をそのまま加算すれば 1 ステップで中心に来るが、実際にはサーボの追従遅延・
機構のバックラッシュ・推論遅延があるため、比例係数を掛けて緩やかに寄せる。

### 2. 制御則

**まず P 制御のみで始める。** 振動が出たら D 項を足す。I 項は原則入れない。

- **P**: 基準ゲイン × `Kp`。`Kp` は 1.0 未満から始める（1.0 に近いほど 1 ステップで寄せに行き、遅延で発振しやすい）
- **D**: オーバーシュート・ハンチングが出た場合に追加する
- **I**: 定常偏差が残る場合のみ検討。機構の自重ドリフトが無ければ不要。積分ワインドアップの
  対策が必要になるため、安易に入れない

> ⚠️ 推論にかかる時間はそのまま制御ループの**むだ時間**になる。むだ時間の大きい系では `Kp` を
> 上げられず発振しやすい。**Phase 1 の推論速度が制御の安定性を直接決める**ため、
> 先に Phase 1 で速度を実測してから Phase 2 に進む。

### 3. デッドバンド

偏差が閾値未満のときは角度指令を出さない。微小な検出ゆらぎでサーボが常時振動するのを防ぐ。
閾値はピクセル単位ではなく角度単位で定義する（解像度を変えても意味が変わらないため）。

### 4. 角度のクランプ

`.claude/rules/hardware.md` の可動域で必ずクランプする。機構保護のため、
制御則の出力を直接サーボに渡さず、常にクランプを通す。

### 5. 検出ロスト時の挙動

1. 一定時間（`lost_hold_sec`）は現在角を保持する — 一時的な検出漏れで動かないようにする
2. タイムアウトしたら探索モードに入る — 既存の `experiment/pan_tilt_camera_check/scripts/explore.py` の
   waypoint 巡回ロジックを流用できる
3. 再検出したら追尾に復帰する

### 6. 検出の間引き（Phase 1 の結果次第）

推論が制御周期に対して遅い場合、毎フレーム検出せず、間を軽量トラッカー（OpenCV の KCF / CSRT 等）で
補間する構成を検討する。OpenCV のトラッカーは C++ にも同じ実装があるため移植性を損なわない。

**Phase 1 で十分な FPS が出れば不要**なので、先に測ってから判断する。

## 実験計画

`.claude/rules/experiment-report.md` に従い、実験ディレクトリごとに `EXPERIMENT.md` を作成する。

### Phase 0 — コードベースの整理 🚧

`experiment/pan_tilt_camera_check/scripts/` にある `servo.py` / `camera.py` を `room_eye/` に移し、
レイヤ分離を完成させる。新しい実験ディレクトリは作らない（実験ではなくリファクタリングのため）。

**済んでいること**: サーボ生成・可動域クランプ・Picamera2 のライフサイクル管理の切り出しと
context manager 化は完了している（`PanTilt` / `PanTiltCamera`）。

**やること**:

- ディレクトリ構成（[ADR-0002](../adr/0002-directory-layout.md)）に沿って `room_eye/` を作る
- `hal/servo.py`・`hal/camera.py` に `PanTilt` / `PanTiltCamera` を移す
- **`clamp` を `control/geometry.py` に移す**。現在 `gpiozero` を import する `servo.py` に同居しており、
  実機なしで import できない。ゴールデンデータ検証の前提が崩れるため優先度が高い
- `hal/` の import を遅延させる（現在はモジュールトップで `gpiozero` / `picamera2` を import）
- `config.py` に `dataclass` ベースの設定と YAML ローダ（deep merge）を実装する
  （現在は `dict` を直接受け渡ししている）
- `config/hardware.yaml` にハードウェア定義を集約する（現在 2 つの YAML に重複している `servo:` ブロック）
- 既存 3 スクリプトを `room_eye` を呼ぶだけの薄い CLI に書き換える
- **`venv/room-eye` に editable install（`pip install -e .`）する**。直接実行したスクリプトの
  `sys.path[0]` はスクリプトのあるディレクトリになるため、これがないと実験スクリプトから
  `import room_eye` できない（`../design/architecture.md`）。`EXPERIMENT.md` の手順にも追加する

**完了条件**:

- `control/` が実機なしで import・単体テストできる
- 実機で既存 3 スクリプトが従来どおり動作する（**挙動を変えないリファクタなので回帰確認が主眼**）
- 構文チェックが通る

### Phase H — サーボ PWM 品質の改善

`experiment/servo_pwm_quality/`

**目的**: 連続保持しながら動かす追尾に耐える PWM 信号品質を確保する。

**検証する選択肢**:

| 案 | 内容 | 見込み |
| :--- | :--- | :--- |
| 1 | **PCA9685（I2C サーボドライバ）** | 専用チップが PWM を生成するため CPU 負荷とジッタが両方消える。C++ 移植も I2C 書き込みだけになり最も単純。部品追加と配線変更が必要 |
| 2 | **ハードウェア PWM ピンへの配線変更** | GPIO14/15 はハードウェア PWM ピンではない。GPIO12/13/18/19 系への変更を検討。部品追加は不要だが `.claude/rules/hardware.md` の GPIO 割当変更が必要 |
| 3 | **ソフトウェア PWM のまま許容する** | 変更コストゼロ。微振動が追尾の実用性を損なわないなら最良 |

**先に確認すること**: `cat /proc/device-tree/model` でモデルを確認する。
`EXPERIMENT.md` のネクストアクションにある「`pigpiod` への切り替え」は、**Pi 5 では使えない**
（GPIO アクセスが RP1 チップ経由に変わり pigpio が対応していない）。Pi 4 以前なら有効な選択肢。

**測定項目**:

- 連続保持中の角度のばらつき（静止指令時の振れ幅）
- 定常状態での CPU 使用率
- 目標角に対する到達精度と再現性

**完了条件**: 採用する PWM 方式が決まり、連続保持中の微振動が追尾に支障ない水準であることを
**定量的に**確認できている（Pre フェーズの目視確認から一段上げる）。

方式を変更した場合は `.claude/rules/hardware.md` の GPIO 割当を更新し、ADR を追加する。

### Phase 1 — 物体検出の実現可能性検証

`experiment/detector_benchmark/`

**目的**: ラズパイ CPU 上で追尾に使える推論速度が出るかを実測し、モデル・入力解像度・ランタイムを決める。

ここで速度が出なければ制御設計自体が変わる（間引き + トラッカー補間が必須になる、あるいは
追尾の応答目標を下げる）ため、Phase 2 より先に測る（`.claude/rules/cv-research.md`）。

**比較軸**（ベースラインを固定し、差分を 1 つずつ変える）:

- モデル: YOLO 系の最軽量クラス（`yolo11n` / `yolov8n` 等）
- 入力解像度: 320 / 416 / 640
- ランタイム: ONNX Runtime / NCNN（`../design/cpp-migration.md`）
- スレッド数

**測定項目**:

- 推論のみの時間、前処理・後処理を含むエンドツーエンド時間、FPS
- メモリ使用量
- **SoC 温度とサーマルスロットリングの有無**（連続運転するため、瞬間値ではなく数分間の持続性能を測る）
- 検出精度の目視確認（自室の実環境で対象を安定して検出できるか）

**完了条件**: モデル・入力解像度・ランタイム・推論パラメータ（conf_thres / iou_thres）が
実測値に基づいて確定し、制御ループのむだ時間の見積もりが出ている。

### Phase 2 — 閉ループ追尾の実装と制御チューニング

`experiment/tracking_control/`

**目的**: 検出結果からサーボ角を決める制御ループを実装し、実機でチューニングする。

**前提**: Phase H と Phase 1 が完了していること。

**進め方**:

1. まず**単軸（パン）のみ**、P 制御のみで成立させる。2 軸同時・PID フルは最初からやらない
2. 静止目標で定常偏差とハンチングを確認し、`Kp` とデッドバンドを詰める
3. 移動目標で追従性を確認し、必要なら D 項を追加する
4. チルト軸を追加する
5. 検出ロスト時の保持・探索復帰を実装する

**測定項目**:

| 指標 | 内容 |
| :--- | :--- |
| エンドツーエンド FPS | キャプチャ → 検出 → 角度指令の 1 周期 |
| 定常偏差 | 静止目標に対する画面中心からのずれ（px および角度） |
| 追従遅延 | 目標が動いてから画面中心に戻るまでの時間 |
| オーバーシュート | 目標角を行き過ぎる量 |
| ハンチング | 定常時の振動の有無と振幅 |
| CPU 使用率 / SoC 温度 | 連続運転時の持続性能 |

**完了条件**: 静止目標を画面中心に保持でき、移動目標に追従できる。ハンチングが実用上問題ない水準。

### Phase 3 — 仕様の凍結とゴールデンデータの作成

**目的**: C/C++ 移植の受け入れ基準を作る。

- 確定したパラメータ値を設定ファイルに固定する
- アルゴリズム仕様を明文化する（`../design/cpp-migration.md` の「移植時に事故りやすい箇所」を必ず埋める）
- **ゴールデンデータを作る**: bbox 座標の時系列を入力、算出されたパン・チルト角の時系列を期待値として記録し、
  `tests/fixtures/` 等の Git 管理下に置く。C++ 版の `control/` に同じ入力を与えて出力一致を検証する

**完了条件**: 確定パラメータ・アルゴリズム仕様・ゴールデンデータが揃い、Python 版なしで
C++ 版の正しさを検証できる状態になっている。

## リスクと対策

| リスク | 影響 | 対策 |
| :--- | :--- | :--- |
| PWM ジッタが解消できない | 追尾中の映像が常にブレる | Phase H で PCA9685 への切り替えを検討。Phase 2 より前に決着させる |
| 推論速度が足りない | 制御のむだ時間が大きく発振する | Phase 1 で先に実測。不足なら間引き + トラッカー補間、または解像度・モデルの見直し |
| むだ時間による発振 | ハンチングが止まらない | `Kp` を下げる、デッドバンドを広げる、D 項を追加する。それでも駄目なら推論速度の改善に戻る |
| サーマルスロットリング | 数分後に FPS が落ちて挙動が変わる | Phase 1 で瞬間値ではなく持続性能を測る。必要ならヒートシンク・ファンを追加 |
| 機構のバックラッシュ | 定常偏差が残る | デッドバンドで許容する。I 項での補正は最後の手段 |
