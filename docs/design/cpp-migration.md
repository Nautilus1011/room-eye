# C/C++ 移植方針

Python で検証した自動追尾を C/C++ で運用版として実装するための方針（`../roadmap.md` の Phase 4）。
ディレクトリ構成は `architecture.md` と [ADR-0002](../adr/0002-directory-layout.md) を参照。

> ⚠️ この文書は Python フェーズ着手時点で書いたものであり、実測に基づかない見込みを多く含む。
> Phase 1 以降で判明した事実に応じて更新すること。

## 移植の考え方

Python フェーズの成果物は Python コードではなく、**検証済みのパラメータ値とアルゴリズム仕様**である。
したがって C++ 移植は「Python コードの翻訳」ではなく「凍結した仕様の再実装」として扱う。

この前提から 3 つの帰結が出る。

1. 設定ファイルは Python / C++ の**両方が同じファイルをそのまま読める**形式に保つ（[ADR-0001](../adr/0001-no-hydra-on-rpi.md)）
2. 制御ロジックは外部依存ゼロにし、1:1 で移植できるようにする
3. **移植の正しさを機械的に検証できる仕組み**をあらかじめ用意する（後述のゴールデンデータ）

## 未決: 全面移植か、hybrid か

**この判断はまだ確定していない。** Phase 1 の実測値が出てから決め、決まった時点で ADR を追加する。

ロボティクスの現場を調査したところ、主流は「Python を全部捨てて C++ にする」ではなく、
**性能critical な層だけ C++ 化し、Python は上位に残して bindings 経由で呼ぶ** hybrid 構成だった。

- 「C++ がコア計算を担い、Python はラッパー経由で高レベルの統合に使う」多言語アーキテクチャ
- 「ロボティクスでは C++ 本体 + Python バインディング、という構成が一般的」
- Python で高速にプロトタイプ → 十分にテスト → **性能が要求する部分だけ** C++ に書き直す

room-eye に当てはめた場合の見立て:

| レイヤ | C++ 化の価値 | 理由 |
| :--- | :--- | :--- |
| `control/` | **高い** | むだ時間の削減が制御安定性に直結する（`../plans/auto-tracking.md`） |
| `perception/` | **高い** | 推論が支配的なコスト。ここの改善がそのまま FPS になる |
| `hal/` | **低め** | `picamera2` / `gpiozero` が優秀で、C++ 化の利得が相対的に小さい |

**ラズパイから Python ランタイムごと外して運用したい**という動機があるなら全面移植が妥当。
そうでなければ hybrid のほうが移植コストとリスクが低い。

いずれを選ぶ場合でも、**bindings は移植検証の足場としては価値がある**（次節）。

## 移植順序

`control/` → `hal/` → `perception/` の順。

`control/` から始めるのは、ゴールデンデータによって**実機なしで検証でき**、
移植の足場（ビルド環境・設定読み込み・テスト基盤）を安全に固められるため。

| 順 | 対象 | 内容 |
| :--- | :--- | :--- |
| 1 | `config` | `struct` 定義 + yaml-cpp での読み込み。Python と同じ YAML を読めることを確認 |
| 2 | `control` | 純粋ロジック。ゴールデンデータで Python 版との出力一致を検証 |
| 3 | `hal` | GPIO・カメラ。実機でしか検証できない |
| 4 | `perception` | ONNX Runtime。同じ `.onnx` を使い、同一画像での検出結果一致を確認 |
| 5 | 統合 | スレッド構成を組み、エンドツーエンドで Python 版と性能比較 |

hybrid を選んだ場合は、各段階の完了時点で bindings 経由の差し替えが可能になるため、
**1 レイヤずつ C++ 化しては実機で動作確認する**という段階移植ができる。
ラズパイ実機 + ハードウェア相手にビッグバン移植をやるとデバッグが困難なので、この点は大きい。

## ゴールデンデータによる言語横断テスト

Phase 3 で作る、移植の受け入れ基準。

Python 版の追尾ループから以下を記録する。

- **入力**: bbox 座標（`x, y, w, h`）とタイムスタンプの時系列、検出ロストのフレーム
- **期待出力**: 制御ロジックが算出したパン角・チルト角の時系列

C++ 版の `control/` に同じ入力を与え、出力が許容誤差内で一致することを検証する。
実機もカメラも不要なため、移植中に何度でも回せる。

これが成立するために `control/` を外部依存ゼロの純粋関数として設計している（`architecture.md`）。
浮動小数点の丸め差があるため、完全一致ではなく許容誤差での比較にする。

配置は `tests/fixtures/`（言語ツリーの外。[ADR-0002](../adr/0002-directory-layout.md)）。
`data/` は Git 管理外なので、**容量の小さい形式（CSV / JSON）に留めて Git 管理下に置く**。

### bindings を作る場合の利点

pybind11 で C++ の `control/` を Python から呼べるようにすると、
**ゴールデンデータ検証が pytest のまま完結する**。C++ 側に別のテストランナーを用意せず、
同じテストコードに C++ 実装を食わせて Python 版との一致を検証できる。

- 作る場合: pybind11 + scikit-build-core などのビルド統合が必要。ラズパイでのビルド時間も増える
- 作らない場合: C++ 側に GoogleTest 等を用意してゴールデンデータを読ませる

導入の判断は Phase 4。ディレクトリ（`room_eye/bindings/` 相当）もその時点で作る。

## ライブラリ対応

| 役割 | Python | C++ | 備考 |
| :--- | :--- | :--- | :--- |
| GPIO / サーボ | `gpiozero` + `lgpio` | `libgpiod` / lgpio の C API | PCA9685 を採用した場合は I2C 直叩きになり、こちらが最も単純 |
| カメラ | `picamera2` | libcamera C++ API | picamera2 は libcamera の薄い Python ラッパ。rpicam-apps を土台にする手もある |
| 推論 | `onnxruntime` | ONNX Runtime C++ / **NCNN** | NCNN は ARM NEON 最適化が効きラズパイ向き。Phase 1 で両方測って決める |
| 画像処理 | `opencv-python` | OpenCV C++ | API がほぼ対応するため移植は容易 |
| 設定 | `PyYAML` | yaml-cpp | `sudo apt install libyaml-cpp-dev` |
| バインディング | — | pybind11 | hybrid または検証足場として採用する場合 |

### 推論ランタイムの選定

Phase 1 で ONNX Runtime と NCNN の両方をラズパイ CPU で実測し、そこで決める。
モデル自体は ONNX で保持し、NCNN を選ぶ場合は変換して使う（元の `.onnx` は残す）。

前処理・後処理を ultralytics に依存せず自前で書いておく方針（`architecture.md`）は、
どちらのランタイムを選んでも移植が同じ作業量で済むようにするためでもある。

### GPIO / PWM

Phase H（`../plans/auto-tracking.md`）の結論に依存する。

- **PCA9685 を採用した場合**: C++ 側は I2C レジスタ書き込みだけになり、移植が最も単純になる。
  PWM 生成を専用チップが担うため CPU 負荷とジッタの両方が消える
- **ハードウェア PWM ピンを使う場合**: `/sys/class/pwm` 経由か libgpiod
- **pigpio は Raspberry Pi 5 では使えない**（GPIO アクセスが RP1 チップ経由に変わったため）。
  Pi 5 で運用する場合は選択肢から外れる

## 並行処理の構造

Python 段階から同じ producer / consumer 構造で書いておく（`architecture.md`）。

```
[capture thread]  --> フレームバッファ --> [inference thread] --> 検出結果
                                                                    |
                                              [control thread] <----+
                                                    |
                                                  サーボ
```

- C++ では `std::thread` + リングバッファ（またはトリプルバッファ）になる
- 制御スレッドは推論スレッドより速い周期で回す。最新の検出結果を保持したまま制御周期を上げる
- Python では GIL があるため真の並列にならないが、**構造を合わせておくこと**が目的。
  推論とキャプチャの待ち時間の重ね合わせは Python でも効く

## 移植時に事故りやすい箇所

Phase 3 の仕様書で必ず明文化すること。

- **角度の符号の定義**。「画像上で右に見える対象を追う＝パン角を増やす方向か減らす方向か」。
  `.claude/rules/hardware.md` は「正面 0°、左右 90°」としか定めておらず、符号は未定義
- **座標系の原点**。画像左上原点、y 軸下向きを前提とする
- **180 度回転補正が適用済みの画像を前提にしている**こと（`.claude/rules/hardware.md`）。
  C++ 側で libcamera を直接叩くとき、補正の適用箇所が変わりやすい
- **角度の単位**（度 / ラジアン）と、パルス幅への変換式
- **時間の単位**（秒 / ミリ秒）。PID の積分・微分項は dt の単位を間違えるとゲインが桁でずれる
