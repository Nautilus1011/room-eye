# ADR-0003: リポジトリのライセンスを MIT から AGPL-3.0 に変更する

## 背景

Phase 1（物体検出の実現可能性検証、`../roadmap.md`）の事前調査で、候補となる物体検出モデルの
ライセンスを整理したところ、**選定の自由度がライセンスによって強く制約される**ことが分かった。

| モデル | ライセンス |
| :--- | :--- |
| YOLO26 / YOLO11 / YOLOv8（Ultralytics） | AGPL-3.0 |
| YOLOv5 / v7 / v9 | GPL-3.0 系 |
| NanoDet / YOLOX / PP-PicoDet / RTMDet（MMDetection 版） | Apache-2.0 |

推論ランタイム（NCNN = BSD-3-Clause、ONNX Runtime = MIT、TFLite = Apache-2.0）はいずれも
permissive で制約にならないため、問題はモデル軸に閉じている。

Ultralytics の[ライセンスページ](https://www.ultralytics.com/license)によれば、AGPL-3.0 の適用範囲は
想定より広い。

- 学習コードだけでなく、**そのコードが生成した学習済みモデルにも及ぶ**
- したがって ONNX / NCNN にエクスポートしても AGPL は外れない
- Enterprise ライセンスが必要な用途として **hardware, edge devices, robotics, cameras, or appliances** が
  明示されている。ラズパイ + カメラ + サーボはこれに該当する
- 準拠する場合の要求は「派生物全体（larger application を含む）のソース公開」

本リポジトリは public な GitHub リポジトリであり、MIT を宣言していた。この状態で Ultralytics 系の
モデルを使うコードを公開すると、AGPL の要求と MIT の宣言が矛盾する。

## 決定

**リポジトリのライセンスを MIT から AGPL-3.0 に変更する。**

これにより、モデル選定においてライセンスを制約条件から外す。

## 理由

**1. AGPL は permissive なコードを取り込めるが、逆はできない**

AGPL-3.0 のリポジトリには Apache-2.0 / MIT / BSD のコードを取り込める。一方 MIT のリポジトリに
AGPL のコードは取り込めない。**AGPL にしておけば候補が最大化される**（Ultralytics 系も NanoDet も
YOLOX も、どれを選んでも整合する）。

Phase 1 の目的は「実測に基づいてモデルを決める」ことであり、測る前にライセンスで候補を
削るのは順序が逆になる。

**2. 個人プロジェクトでは AGPL の義務が実質的に発生しない**

AGPL の義務は「配布」または「ネットワーク越しの提供」で生じる。自室で動かすだけなら義務は生じず、
ソースを GitHub で公開している現状は既にその要求を満たしている。

**3. 商用化の予定がない**

商用利用・proprietary な再配布の予定がないため、copyleft によって失うものがない。
逆に MIT を維持したまま Ultralytics 系を使えば、ライセンス違反の状態になる。

## 結果と影響

**モデル選定への影響**

- ライセンスは足切り条件ではなくなる。Phase 1 では速度・精度・C++ からの利用しやすさで純粋に比較する
- ただし **Apache-2.0 のモデル（NanoDet / YOLOX / PP-PicoDet / RTMDet）を選べば将来の選択肢が広い**という
  非対称性は残る。同等性能なら permissive 側を採る

**リポジトリへの影響**

- `LICENSE` を AGPL-3.0 の全文に差し替える
- `setup.cfg` の `license` メタデータを更新する
- `README.md` の License 節を更新する

**遡及しない範囲**

- **過去に MIT で公開したリビジョンは MIT のまま**である。ライセンス変更は将来のリリースにのみ適用され、
  既に配布済みのバージョンを遡って取り消すことはできない
- 初期コミットのスキャフォールド（`setup.cfg` / `tox.ini` / `.pre-commit-config.yaml` 等）は
  MIT ライセンスのテンプレート由来である。その帰属は `NOTICE` に残す

**C/C++ 移植（Phase 4）への影響**

移植後のバイナリを配布する場合も AGPL が適用され、ソース公開義務が生じる。個人利用の範囲では
問題にならないが、将来の配布形態を変える場合は再検討が必要になる。

**AGPL 第 13 条（ネットワーク条項）**

room-eye をネットワーク越しに他者が操作できる形（Web UI 等）にした場合、その利用者に対して
ソースの入手手段を提供する義務が生じる。GitHub で公開している限り満たせるが、将来 Web UI を
追加する際は意識する必要がある。

## 再検討する条件

- 商用化・proprietary な製品への組み込みを検討する場合
- 他者からのコントリビューションを受け入れる方針にし、AGPL が障壁になる場合
- Phase 1 の実測で Apache-2.0 のモデルが十分な性能を示し、Ultralytics 系を使う理由が消えた場合
  （その場合も MIT に戻すことはできない。AGPL のまま運用するか、AGPL 由来のコードを完全に
  排除したうえで再度ライセンスを変更する判断になる）
